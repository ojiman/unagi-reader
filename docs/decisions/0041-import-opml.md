# 0041 Import subscriptions from an OPML file

- Status: valid (approved by the PdM when the PR that adds this record is merged)
- Date: 2026-10-12
- Decider: the owner (PdM) wanted OPML import. The details below are the Product Owner's.
- Why: a reader is only usable once the person's subscriptions are in it. Typing hundreds of addresses is not an option, and OPML is how every other reader leaves.

## Decision

1. **One entry: File ▸ 「OPMLを取り込む…」** (no key shortcut: it is a rare action). It opens the standard file panel for one `.opml` or `.xml` file. The item is on when the window that shows the library is the active one.
2. **The subscriptions appear at once; the articles follow.** The file is read, and all new subscriptions are added in one save (nothing is fetched first, so a large file does not make the person wait). Then an alert says what happened, and the app fetches the new subscriptions' articles in the background with the normal refresh (it waits for a refresh that is already running). An address that cannot be read shows the usual per-subscription error later; it is not checked at import.
3. **What is read.** Every `<outline>` with an `xmlUrl` (any letter case) is a feed: its name is `title`, then `text`, then the host; `htmlUrl` gives the site (for the icon). An outline without `xmlUrl` that holds feeds is a folder. The app has one level of folders, so a deeper folder is flattened into its top-level folder (Tech ▸ Web ▸ A becomes A in 「Tech」). A folder's name is `text`, or `title` when `text` is empty. A folder with no name, or named 「未分類」 (which is no folder), means unfiled (and so are the feeds of an unnamed top-level folder, even when it holds a named one). A feed outside any folder is unfiled. A feed or folder name is cut to 200 characters.
4. **Existing subscriptions are left alone.** A feed the library already has (compared by its address, with the host in lower case) is not added again and is not moved to the file's folder. The same address twice in the file is one feed (it is not counted as "already subscribed"). Names of existing subscriptions are not changed. A new subscription's name is the file's until its first fetch; then the feed's own title replaces it, as when it is added by address (the person's own renames are kept as always).
5. **Only usable addresses.** `http(s)` with no user name or password. Others are counted, not imported. **A plain `http://` address is changed to `https://`** (the feed's site address too), because the system's transport security does not let the app fetch plain `http://`, so a feed kept at that address would never update. The report says how many were changed. An address with its own port is left as it is. The owner's own Feedly export had 9 of 42 feeds on `http://`; 8 of those answered on `https://` when checked (the ninth was not found at all). If a site has no https, the feed shows the usual error and can be removed.
6. **Safe by the same rules as the feed parser, and a little more.** At most 5 MB, 2,000 feeds, 64 levels (each limit has its own sentence). Every entity declaration is refused when the parser meets it, so an encoding that hides the text (UTF-7) does not get past; a `<!DOCTYPE>` alone is accepted (real files have one, and it is never loaded). Only a regular file is read, opened without waiting and read up to the limit, so a pipe, a device or a huge file behind a link cannot hold the app or fill its memory (「ファイルを開けませんでした。」). A file that is not OPML, not XML, or too big gives one plain sentence, and nothing is added.
7. **The report is short** (the owner asked for fewer words; Apple's guidelines ask for a brief alert title that states the result, and a message only when it helps). The result is the title. The message lists only what was not plain success, and is empty when all went well. A failure has its own title and the reason as the message. There is no sentence about articles arriving: the refresh shows it. The wording is in the specification.
8. **If the save fails, nothing is added** and the error is shown (one transaction with a rollback, like the other store changes). If the save works but loading the list again fails, the report says so and asks the person to open the app again (they are saved; the next refresh brings their articles). The store applies the address rules itself (lower-case host, no fragment, `http(s)` only), whoever calls it.

## Not in this change

Exporting OPML (since decision 0063). Choosing which feeds to import (preview screen). Importing by dropping a file onto the window. Checking every address at import. Measuring a refresh of thousands of new subscriptions: it is the normal refresh (one subscription at a time, three in parallel, on the main actor), which was never run on a library of that size.

## Not verified

The File menu item and the file panel in a real window: the test tools could not press the menu while the owner was working, so the menu item's availability (it needs the active library window), the panel, and the alert are checked only by building the app and by reading the menu list (the item is listed under File). The logic is covered by unit tests: the parser, the one-save import with a failed-save case, the report words, and the whole flow with a stubbed file panel and stubbed feeds (articles arrive after the import; cancel does nothing; a second request while the panel is open is ignored). Checked with one real export (the owner's Feedly file, 42 feeds in 5 folders, kept out of the repository): the parser read all of it, with no unusable address. Not run: other readers' exports, a file with thousands of feeds (the time of its first refresh), Japanese file names. An independent review of the first commit found the points that this text now describes (the reload failure, UTF-7 entities, the counting of repeats, the depth sentence, special files, the wait for a running refresh, the store's own address rules).
